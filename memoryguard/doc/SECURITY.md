# Безопасность MemoryGuard: Защита от side-channel атак KSM

## Введение

Технология KSM (Kernel Samepage Merging) по своей природе создаёт **side-channel** — побочный канал утечки информации. Когда ядро Linux «схлопывает» идентичные страницы памяти в одну физическую, создаётся общее состояние между изолированными процессами. Атакующий может эксплуатировать это общее состояние для чтения данных жертвы.

MemoryGuard реализует **6 модулей защиты**, которые работают на уровне userspace (без модификации ядра Linux) и сужают attack surface.

> **Полный реестр атак (включая Flip Feng Shui и удалённые атаки NDSS 2022), найденные дефекты, остаточные риски и продакшен-профиль: [KSM_THREATS.md](KSM_THREATS.md).**
> Процентные оценки «уровня защиты» ниже экспертные, а не измеренные.

**Предусловия атаки:**
1. Атакующий и жертва работают на **одном физическом хосте**
2. KSM включён и активно сканирует память
3. Память обоих процессов помечена `MADV_MERGEABLE`

## 5 уязвимостей KSM

### Уязвимость 1: CoW Timing Side-Channel (основная)

**Механизм:** атакующий создаёт страницу с «угаданным» содержимым, помечает её `MADV_MERGEABLE`, ждёт пока `ksmd` просканирует и схлопнет, затем замеряет время записи в эту страницу.

**Разница во времени:**

| Состояние страницы | Операция записи | Время |
|---|---|---|
| Приватная (не merged) | Обычная запись в RAM | ~50–200 наносекунд |
| Shared (merged, CoW) | Page fault → выделение новой страницы → копирование | ~2000–4000 наносекунд |

**Пример кода атакующего (концептуальный):**

```c
// Атакующий создаёт страницу с "угадыванием"
char *page = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
                  MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
memcpy(page, guessed_content, 4096);
madvise(page, 4096, MADV_MERGEABLE);

// Ждём, пока ksmd просканирует (sleep ~секунды)
sleep(2);

// Замеряем время записи
struct timespec start, end;
clock_gettime(CLOCK_MONOTONIC, &start);
page[0] = 0xFF;  // Запись → если merged, будет CoW page fault
clock_gettime(CLOCK_MONOTONIC, &end);

long latency = (end.tv_sec - start.tv_sec) * 1e9 +
               (end.tv_nsec - start.tv_nsec);

if (latency > 1000) {
    // Страница была merged → содержимое жертвы = наше "угадывание"
    printf("MATCH! Victim's page contains our guessed data\n");
}
```

**Точность:** побайтовое восстановление памяти жертвы возможно при многократных итерациях.

**Защита MemoryGuard:** Модуль 1 (фильтрация чувствительных регионов) + Модуль 3 (рандомизация + periodic unmerge).

---

### Уязвимость 2: FLUSH+RELOAD через разделённые страницы

**Механизм:** после того как KSM схлопнул страницы, они физически находятся в одном кеш-лайне процессора. Атакующий использует инструкцию `CLFLUSH` для сброса кеша, затем замеряет время повторной загрузки.

**Отличие от Vuln-1:** не требует записи — достаточно чтения + кеш-мониторинга.

**Применение:** определение, какие функции вызывает жертва (профилирование исполнения через общие библиотечные страницы).

**Защита MemoryGuard:** Модуль 1 (blocklist libcrypto, libssl, etc.) — криптобиблиотеки не мержатся.

---

### Уязвимость 3: Covert Channel через KSM

**Механизм:** два вредоносных процесса создают скрытый канал передачи данных. «Отправитель» создаёт/удаляет страницы с определённым содержимым, «получатель» детектирует merge/unmerge через timing.

**Пропускная способность:** ~50–100 бит/сек (низкая, но достаточна для утечки ключей).

**Защита MemoryGuard:** Модуль 3 (periodic unmerge каждые 5–15 мин) + Модуль 5 (anomaly detection).

---

### Уязвимость 4: Memory Probing / Application Fingerprinting

**Механизм:** атакующий создаёт страницы с сигнатурами известных приложений (nginx, Apache, MySQL, etc.) и замеряет, происходит ли merge.

**Результат:** определение ПО жертвы без сетевого сканирования.

**Защита MemoryGuard:** Модуль 4 (whitelist контейнеров, deny-by-default) — вредоносный контейнер не участвует в merge.

---

### Уязвимость 5: CVE-2024-0564 — max_page_sharing Timing

**CVE:** CVE-2024-0564 (CVSS: Low-Medium)

**Механизм:** эксплуатация параметра `max_page_sharing` (default=256). Когда число виртуальных страниц, разделяющих одну физическую, достигает лимита, ядро ведёт себя иначе — это создаёт дополнительный timing-сигнал.

**Защита MemoryGuard:** Модуль 2 (`max_page_sharing = 2`, прямая mitigation).

## 6 модулей защиты

### Модуль 1: Фильтрация чувствительных регионов

**Файл:** `src/main/c/madvise_injector.c`

**Механизм:** при инжекции `MADV_MERGEABLE` в процесс, инжектор классифицирует каждый регион памяти из `/proc/PID/smaps` и пропускает:

1. **`.bss` криптографических библиотек** (~23 штуки + `MEMORYGUARD_EXCLUDE_LIBS`) — анонимный регион сразу за `libcrypto.so` и т.п. (сам код библиотек file-backed и KSM не затрагивается)
2. **Память с признаками секрета** по `VmFlags`: `lo` (mlock), `dd` (MADV_DONTDUMP), `wf` (MADV_WIPEONFORK) — OpenSSL secure heap, libsodium, GnuPG, Vault, состояние RNG
3. **Стеки всех потоков** — `[stack]` и стеки рабочих потоков (по RSP каждого потока)
4. **Kernel-mapped регионы** (`[vvar]`, `[vdso]`, `[vsyscall]`)
5. **Мелкие аллокации** (< 8 KB) — часто содержат ключи/токены

Секреты в общем heap (Java/Go/Node) извне процесса неотличимы от данных — для них работает только политика доверия (модуль 4). `madvise_injector --dry-run <pid>` показывает решение по каждому региону.

**Эффект:** секретные данные физически не попадают в пул KSM → атакующий не может обнаружить их через timing.

---

### Модуль 2: Hardening параметров ядра

**Файл:** `src/main/java/dev/memoryguard/ksm/KsmController.java`

**Устанавливает при старте:**

| Параметр | Значение | Зачем |
|---|---|---|
| `max_page_sharing` | `2` | CVE-2024-0564: сужает timing-сигнал от unmap. **Цена:** экономия на одинаковых ненулевых страницах ≤ 50% (измерено, см. KSM_THREATS.md §5) |
| `merge_across_nodes` | `0` | Изоляция по NUMA-нодам: сужает attack surface |
| `use_zero_pages` | `1` | Нулевые страницы безопасны (не содержат секретов), мержатся для экономии |

Параметры перечитываются после записи. Если страницы уже смержены (EBUSY), агент выполняет `run=2` (при достаточном запасе памяти) и повторяет. Если hardening не подтверждён, инжекция отключается (`MEMORYGUARD_STRICT=true` по умолчанию).

---

### Модуль 3: Рандомизация + Периодический Unmerge

**Файл:** `src/main/java/dev/memoryguard/ksm/KsmTuner.java`

**Три механизма:**

1. **Рандомизация интервалов:** tuner спит 12–20 сек (SecureRandom), а не фиксированных 15. Параметры `pages_to_scan` и `sleep_millisecs` получают ±30% jitter. Атакующий не может синхронизироваться с циклами ksmd.

2. **Периодический unmerge:** каждые 20–60 тиков (~5–15 минут, рандомизировано) записывается `run=2` в sysfs, что заставляет ядро **разъединить ВСЕ** merged-страницы. После паузы 0.5–1 сек KSM перезапускается. Это разрушает любой timing-канал, который атакующий мог построить.

3. **Emergency unmerge:** при обнаружении аномалии `KsmAnomalyDetector` — немедленный unmerge + замедление KSM (sleep=200ms, scan=50) на ~10–13 минут. Если памяти на unmerge не хватает — ksmd замораживается (`run=0`): новые слияния (а значит, и пробы атакующего) прекращаются, достигнутая экономия сохраняется.

**Защита от OOM:** любой `run=2` выполняется, только если после него `MemAvailable` останется > 10% `MemTotal`. На хосте, переподписанном благодаря KSM, глобальный unmerge иначе вызовет OOM-killer.

**Компромисс:** во время unmerge экономия RAM временно обнуляется, но восстанавливается при следующем цикле сканирования. Отключение: `MEMORYGUARD_PERIODIC_UNMERGE=false`.

---

### Модуль 4: Whitelist контейнеров

**Файлы:** `src/main/java/dev/memoryguard/containers/TrustPolicy.java`, `DockerClient.java`

**Принцип:** deny-by-default. Только явно указанные контейнеры получают `MADV_MERGEABLE`. Совпадение **точное** или glob с `*` (раньше — по подстроке, и `evil-redis-x` проходил whitelist `redis`).

Дополнительно: label `memoryguard.ksm=false` (opt-out), label `memoryguard.domain` (домен доверия хоста — `MEMORYGUARD_TRUST_DOMAIN`), запрет хранилищ данных (redis, memcached, БД — цель удалённых атак NDSS 2022). Полные правила — KSM_THREATS.md §3.3.

**Конфигурация:**

```bash
# Только nginx и реплики api-* будут мержиться
MEMORYGUARD_CONTAINER_WHITELIST=nginx,api-*

# Все контейнеры (старое поведение, пониженная безопасность)
MEMORYGUARD_CONTAINER_WHITELIST=*

# Не задано → ни один контейнер не инжектируется
```

**Почему это закрывает атаку:** если вредоносный контейнер НЕ в whitelist, его память НЕ помечена `MADV_MERGEABLE` → ksmd не сканирует её → merge с жертвой невозможен → локальная timing-атака невозможна.

**Чего это НЕ закрывает:** все whitelisted-контейнеры — один домен слияния (дерево KSM общее на хост). И удалённая атака через сетевые запросы к whitelisted-сервису не требует контейнера атакующего.

### Модуль 5: Детектор аномалий

**Файл:** `src/main/java/dev/memoryguard/ksm/KsmAnomalyDetector.java`

**Принцип:** реактивная защита. Если атака уже началась, система заметит аномальные паттерны в KSM-метриках ядра.

**Алгоритм EMA:**

```
EMA(t) = α × Value(t) + (1 - α) × EMA(t-1)

где α = 0.2 (20% вес нового значения)
```

**Правила детекции:**

| Правило | Условие | Интерпретация |
|---|---|---|
| Volatile spike | `rate(pages_volatile) > 25 × EMA` | Массовые CoW page faults → timing probe |
| Sharing spike | `rate(pages_sharing) > 25 × EMA, avg > 10` | Массовое создание merge-кандидатов → probing |
| Volatile ratio | `pages_volatile / pages_sharing > 50%` | Аномальная запись в merged-страницы |

**Реакция на аномалию:**
1. Логирование `[SECURITY]` алерта (также поле `lastSecurityEvent` в `/api/status`)
2. Emergency unmerge (`run=2`), если хватает памяти, иначе заморозка ksmd (`run=0`)
3. Замедление KSM: `sleep_millisecs = 200`, `pages_to_scan = 50` на время cooldown (~10–13 мин)

Детектор смотрит на глобальные счётчики и не атрибутирует атаку конкретному контейнеру. Для атрибуции на новых ядрах доступны `/proc/PID/ksm_stat` и (патч 2025) per-memcg KSM-статистика.

### Модуль 6: Интеграция

**Файл:** `src/main/java/dev/memoryguard/Main.java`

**Порядок инициализации:**
1. `KsmController.applySecurityHardening()` → Модуль 2
2. `KsmAnomalyDetector` → Модуль 5
3. `KsmTuner(controller, anomalyDetector)` → Модуль 3
4. `DockerClient.isContainerTrusted()` в injector loop → Модуль 4
5. `madvise_injector.c` с фильтрацией → Модуль 1

## Сводная таблица эффективности

| Уязвимость | Модули | Механизм | Уровень защиты |
|---|---|---|---|
| CoW Timing (Vuln-1) | 1 + 3 | Фильтрация + рандомизация + unmerge | ~85% |
| FLUSH+RELOAD (Vuln-2) | 1 + 4 | Blocklist crypto libs + whitelist | ~90% |
| Covert Channel (Vuln-3) | 3 + 5 | Periodic unmerge + anomaly detection | ~70% |
| App Fingerprint (Vuln-4) | 4 + 1 | Whitelist + фильтрация | ~95% |
| CVE-2024-0564 (Vuln-5) | 2 | `max_page_sharing = 2` | ~95% |

**Примечание:** 100% защита от KSM side-channel невозможна без отключения KSM или модификации ядра Linux (например, проект FakeDD из Гамбургского университета, который уравнивает время записи для merged и unmerged страниц).

## Рекомендации по среде выполнения

| Среда | Рекомендация |
|---|---|
| **Single-tenant** (все контейнеры доверенные) | Использовать whitelist `*`, все модули включены |
| **Multi-tenant** (разные клиенты на одном хосте) | Строгий whitelist, рассмотреть отключение KSM для непроверенных контейнеров |
| **High-security** (финтех, крипто, государственные) | Отключить KSM полностью (`echo 0 > /sys/kernel/mm/ksm/run`) |
