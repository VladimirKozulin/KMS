# Эксперимент 3, часть 2. Адаптивный тюнер, автозапуск KSM, повторная инжекция

**Дата:** 2026-10-07, 15:25–17:07 (UTC+3). Стенд и нагрузка те же, что в [Отчёт.md](Отчёт.md) §2: 30 контейнеров, ~22 GiB из 25.4 GiB, 2 300 RPS.
**Цель:** максимум экономии памяти при минимальных затратах на сканирование.

## 1. Итог

Адаптивный тюнер (v2) против исходного порогового на одной и той же процедуре: простой → нагрузка → передеплой.

| Показатель | threshold | adaptive v2 | Δ |
|---|---|---|---|
| **Экономия за весь цикл, GiB·мин** | 85 | **104** | **+23%** |
| **Просканировано страниц (работа ksmd), млн** | 39 | **30** | **−22%** |
| **Эффективность, GiB·мин на 1 млрд страниц** | 2 193 | **3 474** | **+58%** |
| Простой: пик экономии, GiB | 8.06 | 8.44 | +5% |
| Простой: время до 90% пика, мин | 8.8 | **5.9** | **−32%** |
| Нагрузка: экономия, GiB | 2.05 | 2.07 | +1% (шум) |
| Нагрузка: скорость сканирования, стр/с | 23 013 | **15 823** | **−31%** |
| Передеплой java-plain: экономия, GiB | 2.02 | 1.95 | −3% (шум) |
| Передеплой: скорость сканирования, стр/с | 24 453 | **10 004** | **−59%** |
| Простой: CPU system, % всех CPU | 1.77 | 2.89 | +63% (цена быстрой сходимости, см. §4) |
| Латентность под нагрузкой p50 / p99, мс | 16.7 / 37.6 | 16.7 / 37.1 | без изменений |

**Вывод.** Объём экономии под нагрузкой ограничен самой нагрузкой (~2 GiB, см. [Отчёт.md](Отчёт.md) §4.3), и его сохраняют оба тюнера. Адаптивный добирается до экономии быстрее и **не платит за сканирование, которое ничего не даёт**. Поэтому за цикл он экономит больше памяти и тратит меньше работы ksmd.

## 2. Что реализовано

| Доработка | Где | Что делает |
|---|---|---|
| Адаптивный тюнер | `ksm/AdaptiveScanPolicy.java`, `KsmTuner.java` | Скорость ksmd по обратной связи (см. §3). `MEMORYGUARD_TUNER=adaptive` (по умолчанию) или `threshold`. |
| Автозапуск KSM | `Main.java` | `MEMORYGUARD_KSM_AUTOSTART=true` включает `run=1`, только если hardening подтверждён. В корневом `docker-compose.yml` включён. |
| Повторная инжекция | `Main.java`, `DockerClient.java` | Каждые `MEMORYGUARD_REINJECT_MINUTES` (10 по умолчанию) процессы инжектируются заново. Инжектор пропускает уже помеченные регионы (`mg`) и метит только новые (рост heap, новые арены). |
| `smart_scan` | `KsmController.java` | Включается при старте (ядро 6.7+): ksmd пропускает страницы, которые раз за разом не сливаются. |
| Наблюдаемость | `/api/status` | `tuner`, `tunerMode`, `tunerRatePagesPerSec`, `tunerReason`, `pagesScanned`, `ksmZeroPages`. |

## 3. Как работает адаптивный тюнер

Раз в 12–20 с (интервал случайный, как и раньше) тюнер читает `pages_scanned`, `pages_sharing + ksm_zero_pages`, `full_scans` и свободную память. Затем он выбирает режим:

| Режим | Когда | Скорость |
|---|---|---|
| **CONVERGE** | старт, unmerge, **первая** инжекция новых процессов ≥ 64 MiB | потолок давления, пока не пройдут 2 полных прохода. Раньше эффективность не измерить: KSM сливает страницу только на 2-м проходе. |
| **TRACK: рост** | чистая эффективность ≥ 1% за окно ~2 мин | ×1.5 |
| **TRACK: churn** | чистая < 1%, валовая ≥ 0.1%: нагрузка ломает слитые страницы, KSM сливает другие, уровень стоит | плавно (×0.85) к «поддерживающей» скорости = 20% потолка |
| **TRACK: тишина** | валовая < 0.1% | ×0.6 до пола |

| Свободно памяти | Потолок | Пол |
|---|---|---|
| < 10% | 100k стр/с | 4k |
| 10–20% | 50k | 2k |
| 20–50% | 20k | 1k |
| > 50% | 10k | 500 |

Скорость переводится в `pages_to_scan` / `sleep_millisecs` пачками по ~20 мс. Jitter ±30% (защита от атак по времени) сохранён.

**Чистая и валовая эффективность.** На записанных данных прогонов 3–5 под нагрузкой после сходимости чистый прирост экономии был **0.0000**. При этом по-тиковые приросты, если отбросить потери, давали 0.006–0.012: нагрузка ломала слитые страницы, KSM сливал другие. Тюнер, смотрящий только на приросты, держал бы ksmd на полной скорости вечно. Поэтому решения принимаются по окну и по двум метрикам.

## 4. Ход работы и итерации

### 4.1. Проверка на записанных данных (до прогона)

Запись прогонов 3–5 прогнана через политику (`PolicyReplay`). Замечание: на записанных данных скорость не влияет на ход сканирования, поэтому это проверка логики, а не результата.

| Фаза | Пороговый (факт) | Адаптивный (решение) |
|---|---|---|
| Сошедшаяся нагрузка (S5, S8) | 54–55k стр/с | 10–17k стр/с |
| Простой, рост экономии (R5) | 27k | 40k |

### 4.2. Прогон adaptive v1 — найдены две ошибки триггеров

| | threshold | adaptive v1 |
|---|---|---|
| Экономия за цикл, GiB·мин | 85 | 106 (+25%) |
| Просканировано, млн | 39 | 48 (**+23%**) |
| Эффективность | 2 193 | 2 230 (+2%) |

Экономия выросла, но сканирования стало **больше**. По журналу решений видно, почему:
1. **Повторная инжекция** раз в 3 мин находила суммарно > 64 MiB новых регионов по 26 процессам: под нагрузкой Python/Node/JVM постоянно создают арены. Это расценивалось как «новая память» и каждый раз запускало CONVERGE на потолке.
2. **Триггер «свободная память упала на 5 п.п.»** срабатывал при каждом старте нагрузки (37% → 30%), хотя рост памяти под нагрузкой — это мусор, а не данные для слияния.

**Исправление (v2):** событием считается только **первая** инжекция новых процессов, то есть новый деплой. Триггер по свободной памяти удалён. Если повторно помеченная память действительно начнёт сливаться, TRACK сам ускорится по чистой эффективности.

### 4.3. Прогон adaptive v2 — журнал решений

| Время от старта | Решение | Почему |
|---|---|---|
| 0:00 | CONVERGE, потолок | старт |
| 7:18 | TRACK, ускорение до 20k | чистая эффективность 19% — нулевые страницы простаивающих JVM |
| 7:57 | TRACK, торможение | «нечего сливать»: экономия вышла на плато 8.4 GiB |
| 15:18 | TRACK, держит 2k | churn под нагрузкой: экономия упала до 2 GiB и стоит |
| 15:36 → 18:51 | ускорение до 42.5k | чистая эффективность 4.3%: повторно помеченные регионы начали сливаться, экономия 1.9 → 2.3 GiB |
| 21:31 | спуск к 10k | churn |
| 22:55 | CONVERGE, 50k | передеплой java-plain: 3.4 GiB новых процессов |
| 25:54 → 28:43 | спуск к 10k | churn |

### 4.4. Повторная инжекция

| Вариант | Первая инжекция | Повторных инжекций | Дополнительно помечено |
|---|---|---|---|
| threshold | 25.4 GiB | 111 | 4.1 GiB |
| adaptive v2 | 18.6 GiB | 101 | 2.3 GiB |

За 30 минут повторная инжекция дотянула до KSM 2–4 GiB регионов, которые раньше не сканировались вообще (рост heap java-plain с `-Xms512m`, новые арены malloc). На этой нагрузке прибавка к экономии небольшая (эпизод 15:36–18:51). Но это покрытие, которого раньше не было.

6–8 ошибок `madvise: Cannot allocate memory` за прогон — безвредная гонка. Процесс освобождает регион между чтением smaps и вызовом, и ядро отвечает `ENOMEM` на диапазон, которого уже нет. Инжектор продолжает со следующего региона.

### 4.5. CPU в простое: +63%

Адаптивный тюнер сходится на 3 минуты быстрее за счёт пика 80–95k стр/с в первые 2 минуты. В 10-минутном окне простоя это даёт +1.1% всех CPU (~0.2 ядра). После сходимости он уходит на 1–2k стр/с, а пороговый держит 8–30k **всё время**. На простое дольше ~15 минут адаптивный становится дешевле. На цикле в целом он уже дешевле (−22% страниц).

## 5. Ограничения

* Сравнение по одному прогону на вариант. Разница в экономии под нагрузкой (+1% / −3%) в пределах шума. Разница в стоимости сканирования (−31% / −59%) и в скорости сходимости (−32%) — нет.
* `pages_scanned` — прямая мера работы ksmd. CPU ksmd на Docker Desktop напрямую не виден, а системное время под нагрузкой зашумлено самой нагрузкой (22–23%).
* Пороги эффективности (1% / 0.1%) и доля поддерживающей скорости (20%) подобраны по данным этого стенда. Для иной нагрузки их стоит проверить: решения тюнера видны в `/api/status` и в логе `[TUNER]`.
* Вариант threshold тоже работал с автозапуском и повторной инжекцией. Сравнивается именно логика тюнера.
